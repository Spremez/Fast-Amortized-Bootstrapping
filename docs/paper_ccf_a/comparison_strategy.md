## 一、竞争格局全景：谁在做摊销自举，各自报什么数

| 方案 | 发表 | 每消息延迟 | 与 686 关系 | 安全处理 | 代码 |
|---|---|---|---|---|---|
| **TFHE-rs (Zama)** | 工业 | 7.10 ms/bit | 686 比它快 2.5–38.7× | 128-bit 声称（LWE 估计器） | Rust 开源 |

**关键发现（读 068 全文后）**：
1. **068 的 Table 7 直接 benchmark 了 686（GP25）**——同机实测：GP25 n=2048 批 5.185s / 摊销 2.53ms；n=8192 批 18.737s / 摊销 2.29ms。**这是我们第一次拿到 686 的第三方同机数据**，可直接校准我们的测量（我们的公平点 n=2048 批 ~12s vs 他们测的原版 5.2s——差异 = 公平 h 42 vs 39 + σ 校正 + 不同 CPU，需标注）。
2. **068 也被 CRYPTO'26 波及**：他们用 LWE Estimator 稀疏档验证安全——恰好是 279 证明"低估攻击"的那个配置。**我们的公平修正框架同样适用于他们**——这是论文的又一差异化点（"我们公平修正了自己的参数，他们也应当"）。
3. **068 的实验关注点**（最新文献的风向标）：(a) **摊销每系数时间**（主指标）；(b) **密钥/密文大小**（BSK 不随 n 增大 = 核心卖点）；(c) **失效概率**（预测 vs 实测，Table 9）；(d) **单线程**（公平架构比较）；(e) 与 TFHE-rs 的倍数。

## 二、论文评测节的对比设计（三层）

### 第一层：直接改进（同机同二进制同安全点）—— SQ vs 686 scalar

这是审稿人最容易验证的主张。表格设计（正在跑的全量 benchmark 直接填入）：

| 参数集 | n | msg 精度 | h_fair | 686 scalar | SQ (q=16) | 加速 | gate |
|---|---|---|---|---|---|---|---|
| SET_2_3_2048 | 2048 | 3 | 42 | 13.1s | 11.7s | **1.10×** | ✓ |
| ...（10 集待收割） | | | | | | | |

**为什么只引同机数**：068 的 2.68ms 是 AWS c8a.xlarge 上的，686 原文数字是另一台机器，TFHE-rs 又是一台——跨机倍数不可靠，这正是 068 强调单线程同机的原因。我们遵守同一原则。

### 第二层：公平安全修正的代价（本文独有的表格）

| | 686 声称安全 | CRYPTO'26 复估 | 公平修正后 | 修正代价 |
|---|---|---|---|---|
| h | 39 | 117–122 bit | h=42 → ≥128 | 时间 +~8%（两方案同担） |
| σ 路线 | 2^-50 | — | σ+15 → ≥128 | stock 崩溃 / SQ +1.1% |

**这张表是审稿人从未见过的**：没有任何前作（686/068/1711）做过多攻击模型下的参数公平化。这是"算法先进性"之外"方法论先进性"的体现。

### 第三层：对位最新竞品（068 / TFHE-rs）——引用级对比 + 复杂度表

| 方案 | 每消息复杂度 | 密钥大小 | 安全模型 | 实测来源 |
|---|---|---|---|---|
| TFHE-rs | O(n·ℓ) | 124 MB | 未修正 | 068 Table 7 |
| 686 scalar @ fair | O(h·ρ) | ~147 MB @ fair | **CRYPTO'26 修正** | 本文实测 |
| **SQ-SAB @ fair** | O(h·ρ) **常数 −10%** | 同上 +0% | 同上 | **本文实测** |
| NTTRU 068 | O(h·ℓpos) | 127–268 MB | **未修正**（同为稀疏档低估） | 068 Table 7 |
| BatchBoot 理论 | Õ(1) 摊销 | ~2.2× | 无 | 未实现 |

**公平性声明（论文必须写明）**：引用 068 的数字时注明"他们未做 CRYPTO'26 修正，其稀疏密钥参数同样应下调安全评估"——不是贬低，是提示读者读倍数时注意安全差。
